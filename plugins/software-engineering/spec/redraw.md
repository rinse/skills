# 仕様書から成果物を描く

スキル `redraw` が担います。
了承された仕様書の差分を成果物に反映する依頼で起動し、統合先のブランチに変更が一つのコミットとして入った状態で終わります。

## 三役

一つの変更は三つの役で運びます。
役を分けるのは、成果物を書く役の文脈から旧版と変更の物語を外すためです。

**オーケストレーター**が書くのは仕様書、書き手への指示、コミットメッセージだけで、コード、テスト、ドキュメントは書きません。
単位の削除と、統合時の衝突の解消は行います。

**書き手**は、テストの書き手と実装の書き手に分かれます。
テストの書き手は担当する節からテストを書きます。
実装の書き手はテストを受け入れ条件として受け取り、テストを変更しません。

- **受け取るもの**：担当する節の全文と語の定義、責務、境界、単位の worktree。実装の書き手はテストも受け取る。差し戻しでは検査役の照合結果も受け取る。
- **受け取らないもの**：変更の物語、会話。
- **読んでよいもの**：worktree 内の全て。旧版は worktree に無く、仕様書は更新後のものがある。他の単位は、既存の部品の再利用と書き方の実例のために読む。境界と他の単位のコードが食い違えば境界に従い、テストと節が食い違えば節に従う。
- **書かないもの**：責務に無いもの。必要だと考えたものは書かずに報告する。
- **報告するもの**：仕様が曖昧で判断した点、仕様に無いが必要と考えた点、境界と他の単位のコードの食い違い、テストが節に無いことを要求している点。
- **終わり方**：成果を worktree のブランチにコミットする。

書き手への指示は常に到達状態で書かれ、「X を Y に変える」という形の指示は存在しません。
差し戻しで渡す照合結果も、不足と過剰と残滓の列挙です。

**検査役**のうち単位の検査役は、担当する節と語の定義、責務、境界、新版を受け取り、旧版があればそれも受け取ります。
旧版を見てよいのはこの役だけです。

## 手順

1. **影響単位を定める。**
   統合先のブランチに対する `spec/` の差分と依頼から影響単位を求め、境界から依存を求めて依存順に並べる。
2. **worktree を用意する。**
   単位ごとにブランチと worktree をプロジェクトルート直下の `.wt/<単位>` に作り、旧版を取り除く。
   worktree には更新後の仕様書がある。
3. **書き手を出す。**
   テストの書き手、実装の書き手の順に出す。
   振る舞いを持たない単位（ドキュメントなど）はテストの書き手を省く。
   依存の無い単位どうしは同時に出す。
4. **単位を検査し、裁定する。**
   差し戻した単位は、書き直しののち再び検査する。
   仕様書に関わる裁定は、その内容を種として `spec` の流れに通し、了承を得てから影響単位を差し戻す。
5. **統合する。**
   依存順に統合し、統合のたびに全体のテストが通る状態を保つ。
   構造表から消えた単位を削除する。
   worktree とブランチを片付ける。
   統合先のブランチには一つの変更につき一つのコミットが残り、そのメッセージに変更の物語を書く。
   書き手の中間コミットは残らない。

push と Pull Request の作成はしません。

worktree を `.wt/` に置くのは、Claude Code のファイルアクセスとコマンド実行の許可がプロジェクトディレクトリに対して与えられており、その配下でだけ書き手が許可を引き継げるためです。

## 単位の検査

実装の書き手が単位を書き上げるたびに行います。
テストは新版の一部として照合します。
三つの照合からなります。

- **過不足**：責務の範囲と新版を両方向で照合する。責務の範囲にある事実で新版が実現していないものが不足、新版の要素で責務の範囲のどの事実にも正当化されないものが過剰である。内部の構造は、それが支える振る舞いや拡張が責務の範囲に無ければ過剰である。
- **隠れた事実の候補**：旧版がある場合に、旧版にあって担当する節に無い振る舞いを挙げる。落としてよいかは判断しない。
- **残滓**：新版だけを読み、コメントアウトされた旧コード、互換のための二重経路、旧概念を指す名前、変更に由来するテスト名、経緯を述べるコメントを挙げる。

不足、過剰、残滓はブロッカーです。
隠れた事実の候補は三種の指摘とは別に報告し、裁定の対象になります。

## 裁定

| 対象 | 裁定 |
|---|---|
| 不足、残滓 | 差し戻す |
| 過剰 | 事実として仕様書に加えるか、差し戻す |
| 隠れた事実の候補 | 事実として仕様書に加えるか、事実ではないと確認して退ける |
| 書き手の報告のうち、仕様が曖昧で判断した点 | 仕様書を一意にする。書き手の判断が採らない読みなら差し戻す |
| 書き手の報告のうち、仕様に無いが必要と考えた点、テストが節に無いことを要求している点 | 過剰と同じ |
| 書き手の報告のうち、境界と他の単位のコードの食い違い | 境界か構造表を直し、影響する単位を差し戻す |

停止は common.md の「検査と停止」によります。
