# 種から仕様書を起こす

スキル `spec` が担う。
ユーザーが種を渡したときに起動し、仕様書の差分をユーザーが了承した状態で終わる。

## 仕様書の規範

仕様書はプロジェクトルート直下の `spec/` にあり、`index.md` が目的、概要、節の一覧を持つ。
節をまたいで使う語の定義と構造表はいずれかの節にあり、語の定義は全ての節の一部として書き手と検査役に渡す。
成果物の書き方への要求と、単位どうしの契約になる公開シグネチャも事実として節に書く。
仕様書は到達状態を書き、手順の途中で成果物が仕様書に遅れても、その差は手順が埋める。

各節は次を満たす。

- 目的は一つで、`index.md` の「目的」に一行で書く。
- 現在真である事実だけを現在形で書く。今も成り立つ理由は事実として書いてよい。
- 何をするかを書き、どうやるかは書かない。手段そのものが要求であるときだけ手段を書く。
- 一つの事実は一箇所にだけ書き、節どうしは矛盾しない。
- 節は単独で読め、用語はその節か語の定義で定義してから使う。
- 二人の書き手が独立に読んで、同じ振る舞いのテストと実装に至る程度に一意である。
- 全ての節に担当する単位があり、全ての単位に担当する節がある。

## 手順

1. 種と仕様書の全文を読む。成果物は種が指す箇所だけ読む。
2. 種が曖昧なら一つか二つだけユーザーに尋ね、残りは自分で埋める。
3. 種が目的か既存の事実と矛盾すれば、根拠の事実を示して却下を提案し、ユーザーが押し通せば矛盾する事実を消す。実現の仕方が複数あれば、案ごとに加わる事実と消える事実を並べてユーザーに選ばせる。種が成果物の不具合を指すなら、仕様書は変えず、その単位を影響単位として 6 に進む。
4. 残る事実、加わる事実、消える事実を分け、規範に従って節を書き、構造表を更新する。
5. 検査役は仕様書の全文を受け取り、何が変わったかを知らされずに規範に照らして読む。矛盾、二通りに読める記述、事実でない記述、担当する単位の無い事実、担当する節の無い単位、一行でない目的がブロッカーである。
6. 仕様書の差分と影響単位の一覧を提示し、了承を得る。了承された差分はコミットせず、作業ツリーに残す。

## 仕様書の無いプロジェクト

プロジェクトの目的を書いたもの（README など）を種とし、成果物の全体を読んで薄い仕様書を起こす。
