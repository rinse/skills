# 種から仕様書を起こす

スキル `spec` が担います。
ユーザーが種を渡したときに起動し、仕様書の差分をユーザーが了承した状態で終わります。

## 仕様書の置き場と規範

仕様書はプロジェクトルート直下の `spec/` に置きます。
`index.md` は目的、概要、節の一覧を持ち、それ自身も節です。
節をまたいで使う語の定義と構造表は節のいずれかにあり、節の一覧がその節を示します。
語の定義は全ての節の一部として扱い、節とともに書き手と検査役に渡します。
節の一覧と構造表は、単位が実現する事実ではなく、オーケストレーターが用いる仕様書の自己記述です。
成果物の書き方への要求（言語、規約、テストの枠組みなど）と、単位どうしの契約になる公開シグネチャも事実であり、節に書きます。

各節は次を満たします。
オーケストレーターは書くときにこれに従い、検査役はこれに照らして読みます。

- 仕様書の目的は一つで、`index.md` の「目的」の章に一行で書く。目的以上の説明は他の章に書く。目的が複数行になるのは、目的以上のことを説明しているか、目的が複数あるかのどちらかである。
- 現在真である事実だけを現在形で書く。経緯、予定、過去の形は書かない。今も成り立つ理由は事実として書いてよい。
- 節どうしが矛盾しない。
- 何をするかを書き、どうやるかは書かない。手段そのものが要求である場合だけ手段を書く。
- 節は単独で読める。用語はその節か語の定義の節で定義してから使う。
- 一つの事実は一箇所にだけ書く。
- 二人の書き手が独立に読んで、同じ振る舞いのテストと実装に至る程度に一意である。
- 全ての節に担当する単位があり、全ての単位に担当する節がある。

仕様書は到達状態を書きます。
手順の途中では成果物が仕様書に遅れますが、その差は予定ではなく、手順が埋めるものです。

## 手順

1. **読む。**
   種の全文と仕様書の全文を読む。
   成果物は、種が指す箇所を確かめるためにだけ読む。
2. **種を理解する。**
   起こせないほど曖昧なら、一つか二つだけユーザーに尋ねる。
   埋められる部分は自分で埋める。
3. **仕様書に照らして判断する。**
   種が目的か既存の事実と矛盾すれば、根拠の事実を示して却下を提案する。
   ユーザーが押し通せば、矛盾する事実を消える事実として扱う。
   種の実現の仕方が複数あれば、それぞれで加わる事実と消える事実を並べ、ユーザーに選ばせる。
   種が指す振る舞いが仕様書と食い違う成果物の不具合であれば、仕様書は変えず、その単位を影響単位として 4 と 5 を飛ばす。
4. **仕様書を更新する。**
   残る事実、加わる事実、消える事実を分け、消える事実は消す。
   規範に従って節を書き、構造表を更新する。
5. **仕様書を検査する。**
   検査役は仕様書の全文を受け取り、何が変わったかを知らされずに、規範に照らして読む。
   知っていると変更点だけを見て、離れた節との矛盾を見逃すためである。
   規範に反する箇所のうち、矛盾、二通りに読める記述、事実でない記述、担当する単位の無い事実、担当する節の無い単位、一行でない目的がブロッカーで、他は後回しである。
   裁定と停止は common.md の「検査と停止」による。
6. **確認する。**
   仕様書の差分と影響単位の一覧を提示し、了承を得る。
   ユーザーが確認するのはコードの差分ではなく仕様書の差分である。
   了承された差分は、`redraw` が取り込むまでコミットされず、統合先のブランチの作業ツリーに残る。

## 導入

仕様書の無いプロジェクトでは、種はプロジェクトの目的を書いたもの（README など）です。
成果物があれば手順 1 でその全体を読み、仕様書を起こします。
起こした仕様書は薄くてよく、成果物にあって仕様書に無い振る舞いは、その単位が書き直されるときに単位の検査が候補として挙げます。
