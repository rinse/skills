# software-engineering

AI エージェントがひとつのプロジェクトに変更を重ね続けても、成果物の質が落ちないようにするためのプラグインです。

## 目的

AI エージェントによる持続可能なソフトウェア開発を実現することです。
ここで「持続可能」とは、変更の回数がいくら増えても、エージェントが仕様と構造を把握し続けられ、次の変更の質が前回の変更の質を下回らないことを指します。

## 問題

現在の AI エージェントは、一発で生成するコードの質に比べて、既存のコードに変更を重ねる作業の質が低い。
アルゴリズムの実装、決まった仕様の実装、TDD による実装は、一発生成なら高い質で仕上がります。
その同じエージェントが同じプロジェクトに数十回の変更を入れると、成果物は少しずつ崩れ、やがてプロジェクトは破綻します。

崩れ方には機構があります。
変更を頼まれたエージェントのコンテキストには、旧い成果物と変更指示と変更理由が同時に載っています。
この条件で最も出やすい出力は、「何が真か」と「何が変わったか」を同時に述べる文やコードです。
旧状態の否定、変更の経緯、理由の混入、コメントアウトされた旧コードが成果物に残り、次の変更はその上に積まれます。
これを繰り返すと、成果物は変更の履歴が地層のように積もったものになります。

地層の害は、一つのファイルが読みにくくなることにとどまりません。
仕様は、最初の仕様書と、その後の会話と、コードに散った但し書きとに分かれ、どこにも全体が書かれていない状態になります。
構造も、変更のたびに足された例外と迂回で当初の設計が読み取れなくなります。
エージェントは把握できない仕様と構造に対して変更を加えることになり、変更の質はさらに落ちます。
この循環が破綻に至ります。

## 方針

崩れる機構が「差分として変更する」ことにあるので、対策は変更を差分として行わせないことです。
変更は、事実集合の更新と、更新された事実からの成果物の再描画として行います。
このプラグインは、そのために次の二つを守らせます。

- **仕様書が唯一の事実集合であり、常に最新である**：
  プロジェクトの仕様は仕様書にだけ書かれ、変更はまず仕様書に入ります。
  コード、ドキュメント、会話のいずれも仕様の出典にはならず、仕様を知りたいエージェントは仕様書だけを読めば済みます。
- **仕様書、コード、ドキュメントは歴史的経緯を含まない**：
  成果物が含んでよいのは、執筆時点で真である内容だけです。
  何がどう変わったか、なぜ変えたかは、Git のコミットメッセージに置きます。
  例外は、履歴を書くこと自体が目的の文書（CHANGELOG、ADR、移行ガイド）だけです。

一つ目が仕様の把握を、二つ目が構造の把握を守ります。
二つが揃うと、どの変更でもエージェントの入力は「変更後の仕様書」だけになり、出力は仕様書から描き直された成果物になります。
差分は Git が記録する副産物であって、エージェントの入力ではなくなります。

## 変更の流れ

変更の依頼を受けたエージェントは、次の順に進めます。

1. 依頼を仕様書に反映する。
   残る事実、加わる事実、消える事実を分け、消える事実は仕様書から消します。
2. 変更が及ぶ成果物の単位を決める。
   コードなら関数やモジュール、ドキュメントなら段落や節のうち、変更が及ぶ最小の自己完結した単位を選びます。
3. その単位を、更新後の仕様書だけから書く。
   旧版を書き換えるのではなく、初めて書くつもりで書きます。
4. 旧版と突き合わせ、意図せず落ちた事実がないかだけを確認する。
   旧版を見るのはこの欠落検出のためだけで、旧版の表現を復元するためではありません。
5. 変更点と理由をコミットメッセージに書く。
