# Git Commit

作業ツリーの変更をコミットするスキル。

## スキル固有の判断

このスキル固有の判断は、作業ツリーの状態と依頼から、どの変更をどの単位でコミットに含めるかを決め、それを一行で表すことである。
作業ツリーにはユーザーの編集や別の作業の変更が同居していることがあり、`git add -A` や「変更のあるファイル全部」では、無関係な変更がコミットに紛れる。

## 今回の作業の変更だけを含める

- 含めるのは、今回の依頼の作業で変えたファイルだけにする。呼び出し元のスキルやユーザーが対象を指定していれば、それに従う。
- 出所の分からない変更や、今回の作業で作っていない未追跡ファイルは含めず、触らずに残して報告で挙げる。黙って含めると、ユーザーの作業途中の変更が別の名目のコミットに入る。
- `.env`、鍵、credentials のように秘密を含みそうなファイルは、ユーザーが明示しない限り含めず、警告する。コミットした秘密は履歴から消しにくい。
- 今回の作業に帰属する変更が一つも無ければ、何をコミットするかをユーザーに尋ねる。Subagent の中など尋ねられない場面では、何もコミットせずにその旨を報告する。

## 関心事ごとにコミットを分ける

変更が複数の関心事にまたがるときは、個別に revert しても意味が通る単位でコミットを分け、分けたことを報告する。
一つの依頼で素直に一つにまとまる変更は 1 コミットにする。
呼び出し元が単位を指定していれば、それに従う。
分けたコミットは、途中のコミットも単体でビルドやテストが通る順に積む。途中で壊れたコミットは bisect や revert の妨げになる。

## default ブランチでは git log で運用を見る

default ブランチ上でコミットしようとしているときは、`git log` でそのリポジトリの運用を確かめる。

- マージを伴わないコミットが default ブランチに直接積まれていれば、そのままコミットする。
- マージコミットや PR 経由の取り込みが並んでいれば、変更内容を表すブランチを切ってからコミットし、切ったことを報告する。ブランチ名は、マージメッセージに現れる既存のブランチ名の付け方に合わせる。
- initial commit しか無いなど判断材料が無ければ、そのままコミットする。

## 対象ファイルを明示してステージする

- `git add path/to/file1 path/to/file2` のように対象を明示的に列挙する。`git add -A` は使わない。前の章で除外した変更を巻き込むため。
- `git add -u` は、追跡中のファイルすべてが今回の作業の分であるときに限って使ってよい。

### 同一ファイルの一部だけをコミットする場合

一つのファイルに今回のコミットと無関係な変更が同居している場合、ハンク選択（`git add -p` / `git apply --cached`）に頼らない。1 行の中に複数の関心事が同居しているとハンクでは物理的に分けられない。適用できるパッチを切り出すより、正しいファイル内容を書く方が確実なので、内容を直接書く。

1. 現在の全内容を、作業ツリーの外の、セッションの一時領域へコピーして退避する。作業ツリーの中に置くとコピー自体がコミットに巻き込まれうる。コンテキストに控えるだけでは、途中で失敗した場合に未コミットの変更が失われる。
2. ファイルを**このコミットに含めるべき内容**に書き直し、`git add path/to/file` してコミットする。
3. 退避したコピーからファイルを書き戻す（残りの変更が作業ツリーに復元される）。

手順 2 が失敗して作業を止める場合も、止まる前に退避したコピーから書き戻し、書き戻したことと退避コピーの場所を報告する。書き直した内容のまま止まると、残りの変更が作業ツリーから消えたように見える。

書き戻したら `git diff` で、残った変更が意図どおりであることを確認する。確認できたら退避コピーを削除する。

## メッセージは慣習に合わせた一行にする

- メッセージは変更内容を端的に表す一行にし、説明の本文は書かない。
- prefix の種類、scope の有無、言語は `git log --no-merges` の既存のメッセージに合わせる。マージコミットのメッセージはツールが自動で付けたものなので、慣習の根拠にしない。慣習が無ければ、`feat:` / `fix:` / `refactor:` / `docs:` / `chore:` などの conventional-commit 風の prefix を付けた英語にする。
- ユーザーやハーネスが求める trailer（`Claude-Session:`、`Co-Authored-By:` など）は、空行を挟んで付ける。一行の規則はこれを妨げない。

例:

- `fix: resolve null pointer in user authentication`
- `feat(dashboard): add CSV export`

## フックの失敗は直して新しくコミットする

pre-commit フックが失敗したときはコミットが作られていないので、原因を直して再度ステージし、新しくコミットする。`--amend` は直前の別のコミットを書き換えるので使わない。`--no-verify` で検査を飛ばすのはユーザーが明示したときだけにする。フックがファイルを書き換えた場合は、書き換え後の差分を確認してからステージし直す。書き換えが今回の変更以外の箇所に及んでも、フックを通すのに要るなら同じコミットに含め、含めたことを報告する。直せない失敗は、フックの出力を示して止まる。

## 報告して止まる

- 既存のコミットの `--amend` は、ユーザーが明示したときだけ行う。push はしない。push するかは呼び出し元かユーザーが決める。
- 報告には、作ったコミット（ハッシュとメッセージ）、含めなかった変更、ブランチを切った場合はその名前を書く。
- コミットせずに終えたときや途中で止まったときは、その理由と、作業ツリーに残っている変更、いるブランチを報告する。呼び出し元が続きを判断できるようにするため。
