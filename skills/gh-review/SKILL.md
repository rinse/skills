# GitHub PR 敵対的コードレビュー

GitHub の PR に対して、独立した懐疑的レビュアーとして反証を行い、inline comment を付けるスキルです。目的は改善提案の列挙ではなく、PR の主張・前提・実装が成立しない可能性のある箇所を壊しに行くことです。

## 前提

- `gh` が必要（無ければ導入を提案する。GitHub MCP があればそれで代替してよい）。GitHub PR でなければ対象外。
- 対象 PR は指定された番号・URL、無ければ現在ブランチに紐づく PR（`gh pr view --json number,title,headRefName,url`）。現在ブランチに PR が無ければ、どの PR かを尋ねる。

```
gh pr view <num> --json title,body
gh pr diff <num>
```

## レビューの姿勢: 反証

1. 作者の意図を好意的に補完しない。判断材料は diff・リポジトリの実コード・一次情報のみ。PR 説明文の主張はそれ自体が反証対象（「説明はこう言っているが diff はそうなっていない」を探す）。
2. 「良い点」は書かない。褒め言葉は反証の密度を薄める。
3. 事実に関する主張は裏を取る。外部 API・ライブラリの仕様、数値、性能は一次情報や実行結果に当たる。diff だけで判断せず、呼び出し元・呼び出し先・型定義など周辺コードを必要なだけ読む。確認できなければ「未検証」と明記する。
4. 確信が持てない指摘も捨てない。偽陽性への配慮は「出さない」ことではなく「確度: 低」と正直にラベルすることで行う。見逃された欠陥は本番で発覚するが、確度ラベル付きの指摘は著者が数秒で棄却できる。

想起の補助（網羅ではない）: 境界条件とエラーパスの握りつぶし、説明文と diff の食い違い、無関係な変更の混入、テストの不在や弱体化、並行性・リソースリーク・部分失敗時の不整合、黙って壊される後方互換性、入力検証・秘密情報・権限。

差分が非常に大きければ、事実の抽出（ファイルごとの変更概要、疑わしい箇所の列挙）だけを安価なモデルの Subagent に委譲してよい。反証の採否・深刻度・確度の判断はレビュアー自身が行う。

再レビュー時は既存のインラインコメント（`gh api /repos/{owner}/{repo}/pulls/<num>/comments --paginate`）を確認し、指摘済みの点や未対応のまま残っている点を新規指摘として重複投稿しない。

## 指摘のフォーマット

```
[深刻度:高|中|低][確度:高|中|低] <何が成立しない可能性があるか（一言）>

- 根拠: なぜそう言えるか。一次情報の出典、または「未検証」。
- 筋の良い修正: 代わりにどう直すのが筋が良いか。方針レベルでよい。
```

- 深刻度は指摘が正しかった場合の影響: 高 = 結論が覆る（バグ、セキュリティ、説明と実装の重大な食い違い）、中 = 修正が必要、低 = 特定の前提が崩れたときだけ問題。
- 確度は指摘自体の確かさ: 高 = 裏を取った、中 = 状況証拠のみ、低 = 推測を含む。
- 二軸は独立。「深刻度: 高 / 確度: 低」（当たっていれば致命的だが未確認）はまさに著者に見てほしい指摘。

inline comment は diff のハンク内の行にしか付けられない（外の行は API が 422 を返す）。追加行・コンテキスト行は新ファイル側の行番号で `side: RIGHT`、削除行は旧ファイル側で `side: LEFT`、複数行は `start_line` と `line`。根拠がハンク外にあるなら、ハンク内の関係する行に付けて本文で引用する。

## 確認と投稿

レビュー投稿は関係者に通知される取り消しづらい操作なので、全体サマリーと各コメント（ファイル:行、タグ、本文）を提示して了承を得てから投稿します。

1 件ずつではなく 1 つのレビューにまとめて投稿する。レビュー本文の末尾に「反証を試みたが壊せなかった点」を 1〜2 行書く（褒め言葉ではなく検証範囲の報告。無ければ「なし」）。`event` は `COMMENT` 既定で、`REQUEST_CHANGES` / `APPROVE` は明示的に求められたときだけ。PR をブロックするかはユーザーの判断。

```json
{
  "event": "COMMENT",
  "body": "反証の観点でレビューしました。\n\n反証を試みたが壊せなかった点: エラーパスの網羅とトランザクション境界は攻めたが破綻を見つけられなかった。",
  "comments": [
    {
      "path": "src/auth.py",
      "line": 42,
      "side": "RIGHT",
      "body": "[深刻度:高][確度:高] 空入力で例外になり、認証全体が落ちる可能性\n\n- 根拠: この分岐に null チェックがなく、呼び出し元 `login_handler` (src/handlers.py:88) は未検証の入力をそのまま渡している（実コードで確認）。\n- 筋の良い修正: この関数の入口で空・null を早期 return で弾く。"
    }
  ]
}
```

```
gh api --method POST /repos/{owner}/{repo}/pulls/<num>/reviews --input review.json
```

投稿後、レビューの URL（応答の `html_url`）を報告する。
