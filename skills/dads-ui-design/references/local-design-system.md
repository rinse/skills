# ローカルデザインシステムの決定と作成

デジタル庁デザインシステムウェブサイト https://design.digital.go.jp/dads/ のコンテンツを加工して作成。
出典：https://design.digital.go.jp/dads/guidance/local-design-system/ 、https://design.digital.go.jp/dads/foundations/color/

ローカルデザインシステムは、DADS を導入先の要件に合わせて定義したデザイン仕様（スタイルガイド）。DADS はブランドを持たないプラットフォーム型なので、使う前にこれを決める。
このファイルのうち「DADS の手順」の節は DADS の記述の要約、それ以外（既存の検出、3 つの選択肢、記録ファイル、コードでの上書き、検証スクリプト）はこのスキルの方法。

## 1. 既存のものを探す

次の順に探す。

1. 記録ファイル `docs/design-system.md`。プロジェクトにデザイン文書の置き場所の慣習があればそちらを先に見る。
2. スタイルガイドに相当する文書（`design-system`、`styleguide`、`スタイルガイド` を名前に含むファイルなど）。
3. `--color-key-*` を上書きしている CSS、`@digital-go-jp/design-tokens` や `@digital-go-jp/tailwind-theme-plugin` の導入と設定。
4. README や AGENTS.md などから参照される Figma のファイル。

ロゴの使用規定、ブランドカラー、ブランドガイドラインの PDF などのブランド資産だけが見つかった場合、それはローカルデザインシステムではない。選択肢 2 の入力として扱う。

## 2. ユーザーに選んでもらう

記録ファイルがすでにあれば選択肢 1 として扱い、聞き直さない。無ければ、見つかったものを示して次から選んでもらう。

1. **既存のものを使う**：リポジトリで見つかったもの、またはユーザーが示す Figma や文書。
2. **固まっている部分だけ指定する**：キーカラーなど決まっている値だけを受け取り、残りを DADS の様式に沿って導出する。
3. **すべて任せる**：DADS の初期値（デジタル庁ウェブサイト由来）をそのまま使う。

どれを選んでも、結果を記録ファイルに書く（後述のテンプレート）。次回以降はその記録を選択肢 1 として読む。

### 選択肢 1：既存のものを使う

- 既存の定義を DADS の初期値より優先する。定義が無い項目だけ DADS の初期値で補う。
- 既存の定義を SKILL.md の「守る要件」と照合し、違反（キーカラーのコントラスト不足、変更されたフォーカスインジケーター、14px 未満の本文など）があればユーザーに報告する。黙って直さない。
- リポジトリ外のもの（Figma など）なら、決まっている値を記録ファイルに書き写す。

### 選択肢 2：固まっている部分だけ指定する

ユーザーから受け取るのは、決まっている値だけでよい。多くの場合はキーカラー（ブランドカラー）で、角丸、フォント、余白の単位が加わることがある。導出は次の順に行う。

**キーカラー**

1. ブランドカラーに近い色相のプリミティブカラーがあれば、その 13 段階（50〜1200）を `--color-key-*` に割り当てる。DADS がキーカラーの例として挙げる色相は Blue、Green、Neutral、Light Blue、Cyan、Orange、Purple。Neutral はグレーの段階がキーカラーの段階と一致しないため、使う場合は Figma データのバリアブルの定義に従う。
2. ブランドカラーがどの色相にも近くない、またはプライマリーとしてコントラストが足りない場合、DADS は次のどちらかを示している。
   - ブランドカラーと同じ色相で明度を調整し、キーカラーにする。
   - ブランドカラーはロゴと装飾だけに使い、キーカラーはブランドカラーと相性のよい色をコントラスト要件の範囲で選ぶ。
3. 同じ色相で独自の 13 段階を作る場合、その作り方は DADS に規定が無い。このスキルでは、ブランドカラーの色相を保ったまま、明度の並びが同じ段階のプリミティブカラー（Blue など）に近くなるように作る。
4. どの方法でも、`scripts/contrast.py --key` で検証する。

```sh
python3 scripts/contrast.py --key '#e6f5ec' '#c2e5d1' '#9bd4b5' '#71c598' '#51b883' '#2cac6e' \
  '#259d63' '#1d8b56' '#197a4b' '#115a36' '#0c472a' '#08351f' '#032213'
```

検証する組み合わせは、DADS の HTML 版コードスニペットで `--color-key-*` が使われている箇所から集めた 15 組（白地の文字、塗りボタンの白文字、淡色背景の上の文字、チェックボックスなどの非テキスト）。プリミティブカラーをそのまま割り当てた場合の結果は次のとおり。

| 色相 | 結果 |
| --- | --- |
| Blue（初期値）、Light Blue、Purple | すべて満たす |
| Green、Cyan | key-900 on key-300 が不足（日付ピッカーのカレンダーボタン押下時） |
| Orange | key-900 on key-200 と key-300 が不足（同ボタンのホバー時と押下時） |
| Magenta | key-900 on key-300 が不足 |
| Lime、Yellow、Red | 複数の組み合わせが不足（DADS のキーカラーの例にも無い） |

不足が特定のコンポーネントの状態だけなら、色相を捨てずに、その状態の文字色を 1 段濃くする（key-900 を key-1000 にするなど）。どう直したかは記録ファイルに書く。

**キーカラーから決まる役割**

- プライマリー：key-900 を基本にする（初期値の塗りボタンの背景、チェックボックスの色）。主要な背景色に対して 4.5:1 以上。
- セカンダリーとターシャリー：同じ色相で、一方を明度の高い段階、もう一方を明度の低い段階にする。背景に隣接する要素なら 3:1 以上、文字なら 4.5:1 以上。
- バックグラウンドカラー：使うなら淡い段階（key-50 など）にし、その上に置く文字と要素のコントラストを確認し直す。

**キーカラーに合わせて動かさないもの**

- フォーカスインジケーター（Yellow-300 と黒）。
- セマンティックカラーの色相。キーカラーと同じ色相（緑、赤、黄、橙）になる場合も意味の対応は変えない。キーカラーの要素とエラーなどの表示が色だけで見分けにくくならないよう、アイコンやテキストでの区別を確実にする（このスキルの判断）。
- リンクの色。初期値の青と紫のまま使う。DADS はブランドの色相を使うことも禁止していないが、その場合はコントラスト、色覚多様性、リンクと認識できることを確認する。

**その他の値**

指定が無いものは DADS の初期値を使う。フォントは Noto Sans JP、余白は 8px 基準、角丸とエレベーションはトークンの値、ブレークポイントは 768px。角丸を指定された場合は、コンポーネントの大きさごとに印象が揃うように調整する。

### 選択肢 3：すべて任せる

DADS の初期値をそのまま使う。キーカラーは Blue。記録ファイルには「DADS の初期値をそのまま使用」と、基にした DADS の版だけを書く。

## 3. 記録ファイル

既定の保存先は `docs/design-system.md`。DADS はローカルデザインシステムの構成を規定していない。以下はこのスキルの最小のテンプレートで、必要な項目を自由に足してよい。

```markdown
# <サービス名> ローカルデザインシステム

- ベース：デジタル庁デザインシステム（ドキュメント 2026-10-13 版、デザインデータ v2.18.0）
- 決め方：<既存のものを使用 / 指定値から導出 / DADS 初期値をそのまま使用>

## ブランドとコミュニケーション方針

<ロゴの使用規定、ブランドカラー、トーン。無ければ「なし」>

## 基本デザイン

DADS の初期値から変えたものだけを書く。書いていない項目は DADS の初期値。

| 項目 | 値 | 理由 |
| --- | --- | --- |
| キーカラー | Green（primitive-green-50〜1200） | ブランドカラー #xxxxxx に近い色相 |

## コントラストの検証

`scripts/contrast.py --key` の結果と、不足に対して行った調整。

## 使用するコンポーネント

<使うものと、使わないもの。ラベルを固定したボタンや、組み合わせを固定したセットがあれば書く>

## 独自の定義

<DADS の定義で足りずに追加したもの>
```

コードでは、キーカラーの参照先を差し替える。

```css
:root {
  --color-key-50: var(--color-primitive-green-50);
  --color-key-100: var(--color-primitive-green-100);
  /* ... 1200 まで同様 */
}
```

Tailwind CSS のテーマプラグインを使っている場合の上書き方法は、プラグインの README で確認する。

## DADS の手順（Figma）

DADS のガイダンスが示す作成手順の例。ブランドやコミュニケーション方針を最初に定め、次にスタイル定義を更新し、最後に UI コンポーネントを調整する。

1. Figma Community からデザインデータを取得する。
2. ファイル名、カバーのタイトル、バージョン番号を導入先の体系に変える。
3. ブランドアセットなどに基づいてデザイントークンのルールを決め、Figma のバリアブルでキーカラーを置き換える。プリセットから選ぶか、独自のカラーパレットを作って差し替える。
4. 使うコンポーネントを選び、使わないものは削除するか別の領域に移す。
5. 決めたルールに基づき、コンポーネント単位で角の形状や余白を調整する。
6. よく使うボタンのラベルなどを入力した状態でコンポーネントとして定義する（作業効率が上がり、文言の揺れを防げる）。
7. 組み合わせが定まっているコンポーネントのセットを定義する。

並行して画面仕様書（ワイヤーフレームなど）を定義済みコンポーネントで作り、調整が必要になった点をコンポーネントの定義に反映する。提供された構成のままで実現できない場合は、コンポーネントを detach して組み直し、ローカルデザインシステムのコンポーネントとして定義し直してよい。
