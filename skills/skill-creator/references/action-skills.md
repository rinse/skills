# 外部に作用するスキルと委譲するスキル

PR、Issue、レビュー、マージ、リリース、タグ、push のように外部に作用するスキルと、Subagent に作業を委譲するスキルに共通する取り決め。
ここにある定型は、各 SKILL.md には一行ずつ書けば足りる。
本文は、そのスキル固有の判断に使う。

## 共通骨格

外部に作用するスキルは、ほぼ次の流れを踏む。

1. **ガード**：依存ツールの有無と、対象が適用範囲内かを確かめる。
2. **収集**：差分、ログ、テンプレートを読む。
3. **合成**：タイトル、本文、バージョンなどを組み立てる。
4. **確認**：実行前にユーザーへ提示して了承を取る。
5. **実行**
6. **後処理**：一時ファイルを片付け、結果（URL など）を報告する。

骨格は共有するが、各 SKILL.md に手順書として書き写さない。

## 実行前の確認と保守的な既定

関係者に通知される操作や公開される操作は取り消しづらいので、実行前に内容を提示して了承を取る。
修正指示があれば反映して再提示する。

強い副作用のあるオプションは、ユーザーが明示しない限り付けない。

- PR の draft 化、担当者、マイルストーンは、希望されたときだけ付ける。
- レビューの event は `COMMENT` を既定にする。重大な指摘があっても、PR をブロックするかはユーザーが決める。
- ラベルは既存ラベル（description も読む）から内容に確信を持てるものだけを選ぶ。存在しないラベルは作らずにユーザーに確認する。
- 確信の持てない指摘を出すときは、確度が低いと明示して、受け手がすぐ棄却できるようにする。

## push

push と、push を誘発する操作は、まず一度試す（`git push origin <branch>`）。
認証や対話的なパスフレーズ入力で失敗したら繰り返さず、失敗の内容と実行してほしいコマンドを示してユーザーに依頼する。
upstream を設定するかどうかのような利用者ごとの好みは、スキルに埋め込まない。

## git の規律

- コミットメッセージは単一行で、conventional-commit 風の prefix を付ける。コミットは git-commit に引き渡す。
- `git add -A` は使わず、対象ファイルを列挙する（`git add -u` は可）。
- default ブランチ上で作業を始めるときは、先にブランチを切る。

## ツールの検出と適用範囲

依存ツールはガードで `command -v <tool>` により確かめ、無ければ導入を提案する。
導入手順は書かない。
手順が非自明なツールに限り、手順を `references/` に分ける。

「ツールが未導入」と「スキルの適用範囲外」は区別して書く。

- `gh` が無い場合は、導入を提案する。
- GitHub リポジトリでない場合（別ホストのリモート、リモート未設定など）は、何もせず対象外と伝えて終える。
- 対象はあるが特定できない場合（現在のブランチに PR が無いなど）は、黙って止まらずどれを対象にするか尋ねる。

`gh` が使えず GitHub MCP が使える環境では MCP で代替してよい、と一行書く。
MCP 用の手順は書かず、確認や push の方針も変えない。
`gh` の GraphQL 系サブコマンドが 403 で拒否される環境（クラウドセッションなど）に備え、必要なら `gh api` による REST の読み替えを添える。

## ペイロードとテンプレート

本文やコメントのような複雑な文字列はコマンドラインに直書きせず、ファイルに書き出して渡す（`--body-file`、`--notes-file`、JSON を `--input` で渡すなど）。
一時ファイルの置き場所はハーネスの案内に従えばよいので、SKILL.md には書かない。

PR や Issue のテンプレートは所定のパスで探し、あれば各セクションを実内容で埋め、無ければスキル側のフォールバックを使う。
プレースホルダやコメントを残さない。

## Subagent への委譲

委譲するのは、担当範囲だけを見れば進められ、他の作業とのずれを後段のレビューで正せる作業のうち、オーケストレーターのコンテキストを圧迫するものに限る。
一貫性と最終判断はオーケストレーターが握り続ける。
委譲の主目的は、オーケストレーターのコンテキストを空けてワークフロー全体を見渡し続けることにある。
安価なモデルを選べることによるコスト削減は副次的な利点にとどまる。

- 差分の読解のような事実抽出だけを委譲するときは、判断（bump 種別やバージョンなど）をさせない。オーケストレーターが自分の読んだログと報告を突き合わせて決める。
- 並列開発では、タスク分解、レビュー、マージをオーケストレーターに残す。全タスクの差分を一人が読むことが、重複実装や命名のずれを防ぐ。

モデルは難易度で割り当てる。
判断の余地がほぼない機械的な作業は Haiku、仕様が明確で局所的な変更は Sonnet、設計判断や複数モジュールにまたがる作業は Opus に振る。
一段上のモデルに上げる前に、一段下のモデルに具体的な指示を与えて届かないかを検討する。
弱いモデルほど、変更対象のファイル、倣うべき既存コード、受け入れ条件まで指示を具体的にする。

worktree はプロジェクトルート直下の `.wt/` に作り、`.wt/` は `.git/info/exclude` に入れる。
Claude Code の許可はプロジェクトディレクトリに対して与えられるので、`/tmp` や Agent ツールの `isolation: "worktree"` が作るプロジェクト外の場所では Subagent が作業できない。
