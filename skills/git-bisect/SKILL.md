# Git Bisect

回帰バグを持ち込んだコミットを `git bisect run` で特定し、根拠とともに報告するスキル。

## スキル固有の判断

このスキル固有の判断は、探索範囲のどのコミットでも同じ基準で症状の有無だけを 0 / 1 / 125 で返す述語スクリプトを合成し、反復を `git bisect run` に任せることである。

各ステップをエージェントが手で試してはいけない。`git bisect good` / `git bisect bad` を手で繰り返したり、途中のコミットを一つずつ checkout して試したりすると、次の二つが起きる。

- bisect が探索を対数回に抑えても、その利点をエージェントのターン数で使い切る。
- ステップごとに違うコマンドや違う観察で症状を判定してしまい、途中で基準が揺れると結論が丸ごと狂う。述語スクリプトに固定すれば、全ステップで同じ基準が使われる。

手で述語を実行してよいのは、本走の前の校正（bad と good で 1 回ずつ）だけである。
修正はこのスキルの範囲外とする。

## 再現コマンドを一つに確定してから始める

- git リポジトリでなければ、対象外と伝えて終える。
- 述語の中核は、次の契約を満たす再現コマンドである。
  - 単一コマンドで実行でき、症状が出たら非 0、出なければ 0 で終わる。
  - テストフレームワーク経由なら、該当するテスト 1 件だけを走らせる（`pytest path/to/test_x.py::test_y` など）。他のテストの失敗が判定に混ざらないためである。
  - 間欠的にしか再現しないなら、再現率（20 回中 3 回失敗など）を添える。述語の反復回数をこれで決める。
- ユーザーがそういうコマンドを持っていればそれを使い、この契約を満たすことだけを確かめる。
- 無ければ、先にこの契約を満たす再現テストか再現スクリプトを作る。いきなり述語を書かない。
- 再現できなければ bisect に進まず、再現できなかったと報告して終える。

## good と bad は祖先関係を確かめて決める

- bad は症状が出るコミットで、通常は `HEAD` か報告された版（タグ、SHA）である。
- good は症状が出ないと分かっているコミットで、最後のリリースタグや、ユーザーが「この頃は動いていた」と言う版である。
- good が不明なら、`git tag` や `git log --until=<date>` から候補を挙げてユーザーに選んでもらう。古いコミットを片端から試すのは手動反復と同じで無駄が多い。
- good は bad の祖先でなければならない（`git merge-base --is-ancestor <good> <bad>`）。祖先でなければ端を選び直す。
- 浅いクローンで good まで履歴が無ければ、`git fetch --unshallow` を提案してユーザーに尋ねる。勝手に取得しない。

## 述語は症状だけを bad と判定する

`git bisect run` は述語の終了コードを次のように解釈する。

| 終了コード | 意味 | 返す場面 |
|---|---|---|
| `0` | good | 症状が出なかった |
| `1`–`127`（`125` を除く） | bad | 症状に固有の印が出た |
| `125` | skip | ビルド失敗、依存の導入失敗、症状と無関係な失敗、タイムアウト |
| `128` 以上 | bisect 全体を中断 | 返さない。`1` か `125` に変換する |

bad を返すのは、その症状に固有の印（特定の assertion の失敗、特定のエラー文、特定の誤った出力）が出たときだけにする。
再現コマンドの非 0 をそのまま bad にすると、新しい API を参照するテストが古いコミットで ImportError などにより落ち、症状と無関係なコミットが bad と判定される。両端の校正ではこの中間のコミットの誤判定を防げない。
それ以外の失敗は `125` にして、bisect に近傍のコミットで代替させる。
印は bad での再現コマンドの出力から選び、good での出力には現れないことを確かめる。

再現コマンドは `timeout` で包み、上限は校正で測った実行時間の数倍にする。テストがハングすると run が止まらないためである。タイムアウトは `125` にする。ただし症状そのものがハングなら bad にする。

述語は次の 3 段で書く。

```sh
#!/usr/bin/env bash
set -u

# (1) 依存の導入とビルド。失敗は症状と無関係なので skip
<install deps per lockfile> || exit 125
<build> || exit 125

# (2) 再現コマンドの実行と出力の保存
out=$(timeout <limit> <repro command> 2>&1); rc=$?

# (3) 症状の印があれば bad、成功なら good、それ以外は skip
if [ "$rc" -eq 0 ]; then exit 0; fi
if [ "$rc" -eq 124 ]; then exit 125; fi
printf '%s\n' "$out" | grep -q '<symptom signature>' && exit 1
exit 125
```

ユーザーの再現コマンドが逆向き（症状が出たら 0）なら、(3) を反転させる。向きを取り違えると結論が逆になるので、校正で確かめる。

## 述語と再現テストは worktree の外に置く

bisect は checkout を繰り返すので、作業ツリーの中に置いたファイルは消えるか、過去の同名ファイルと衝突する。

- 述語スクリプトと再現テストの原本は、worktree の外のセッションの一時領域に置き、`git bisect run` には絶対パスで渡す。
- 未コミットの再現テストは、worktree の元にした `<bad>` には含まれていない。フレームワーク経由のテストのようにツリー内の所定のパスに無いと動かないものは、述語の (2) の前に原本をそのパスへコピーし、実行後に消す。テストが読み込む未追跡のファイル（fixture、conftest など）も同様にする。そのパスがそのコミットで追跡されていれば、消さずに `git checkout -- <path>` で戻す。残すと、次の checkout が「untracked working tree files would be overwritten」で止まる。途中の `exit` でも漏れないよう、後始末は `trap '<後始末>' EXIT` に書く。
- 探索範囲が長く、テストランナーの版が範囲の中で変わるなら、ランナーに依存せず単体で動く再現スクリプトに置き換える。範囲全体で同じ 1 本が動けば、判定基準が一定に保たれる。範囲が短ければ、ランナー起因の失敗を `125` にするだけでよい。

## 依存は述語の中でコミットごとに入れる

新しい worktree には、追跡されていない依存（`node_modules`、仮想環境、ビルド成果物など）が無い。
述語の (1) で、そのコミットの lockfile どおりに依存を入れる（`npm ci`、`uv sync` など）。範囲の中でパッケージマネージャが変わっていれば、そのコミットにある lockfile で入れ方を選ぶ。失敗したら `125` を返す。
メインの checkout の依存を流用しない。探索範囲の中で依存の版が変わると、古いコードを新しい依存で判定することになる。

## フレーキーな再現は反復して固める

bisect は、同じコミットを測れば同じ答えが出ることを前提とする。
再現コマンドに再現率が添えられていたら、述語の (2) で再現コマンドを N 回繰り返す。1 回でも症状の印が出たら bad、N 回とも成功したら good、印の無い失敗やタイムアウトが混ざったら skip にする。
再現率が分からなければ、校正の前に bad で再現コマンドを繰り返して測る。

N は、再現率 p のとき N 回とも症状が出ない確率 (1−p)^N が 1% 以下になるように選ぶ。p=0.15 なら N=30 で約 0.008 になる。
N 回繰り返すぶん実行時間が伸びることを、本走前の見積もりに含める。

## worktree を作ってから述語を校正する

bisect はメインの checkout を占有せず、未コミットの変更と混ざらないよう、プロジェクトルート直下の `.wt/bisect` で回す。
エージェントのファイルアクセスとコマンド実行の許可はプロジェクトディレクトリに与えられているので、その配下に置く。`.wt/` はリポジトリを汚さないよう `.git/info/exclude` に入れる。

```sh
git check-ignore -q .wt || echo '.wt/' >> .git/info/exclude
git worktree add --detach .wt/bisect <bad>
```

`--detach` を付けるのは、`<bad>` がメインの checkout で使っているブランチ名だと、付けない限り作成に失敗するためである。

`.wt/bisect` が既にあり、このセッションで作ったものでなければ、前回の調査の途中経過が残っている可能性がある。黙って消さず、`git -C .wt/bisect bisect log` の内容を示して、片付けて作り直すかをユーザーに尋ねる。

worktree の中で、本走の前に述語を 1 回ずつ実行して校正する。校正はメインの checkout では行わない。good へ切り替えると未コミットの変更とぶつかるためである。

```sh
git -C .wt/bisect checkout --detach <bad> && (cd .wt/bisect && /abs/path/to/predicate.sh); echo $?   # 非 0 であること
git -C .wt/bisect checkout --detach <good> && (cd .wt/bisect && /abs/path/to/predicate.sh); echo $?  # 0 であること
```

各実行にかかった時間を測っておき、タイムアウトの上限と本走の見積もりに使う。

校正が通らなければ、まず述語を直す（向きの取り違え、ビルド段の不足、症状の印の誤り、パスの誤り）。
直しても通らなければ、端の選び方を疑う。good が実は既に壊れている、bad が実は症状を出さない（症状が未コミットの変更にしか無い場合を含む）などである。そのときは状況と端の候補を示し、選び直しをユーザーに尋ねる。

## 反復は git bisect run に任せる

本走の前に、所要時間を「ステップ数（`git rev-list --count <good>..<bad>` の log2）× 校正で測った 1 回の時間」で見積もる。
見積もりが 30 分程度を超えたら、見積もりを示して了承を取ってから走らせる。それ以外は確認せずに走らせる。
Subagent の中などユーザーに尋ねられない場面で見積もりが長い場合は、走らせずに止まる。見積もり、述語のパス、校正の結果、残した worktree の場所を報告し、走らせるかの判断を呼び出し元に委ねる。

```sh
cd .wt/bisect
git bisect start <bad> <good> [-- <paths>]
git bisect run /abs/path/to/predicate.sh
```

- `git bisect start` の第 1 引数が bad、第 2 引数が good である。
- 変更が特定のディレクトリに限られると分かっているときだけ、`-- <paths>` で範囲を絞る。そのパスに触れないコミットを探索から外せるので、ステップ数が減る。ただし範囲の外で入った原因は見落とすので、絞ったことを報告の弱点に書く。
- run が `<sha> is the first bad commit` を出すまで、反復に手を出さない。

run が 1 コミットに収束せずに終わることもある。どちらの場合も、推測で 1 つに断定しない。

- `only skipped commits left` で候補が複数残った場合：skip の原因が述語の不備（古いコミットに合わないビルド手順など）なら、述語を直して再走する。本当に判定できないコミットなら、候補の範囲のまま報告する。
- 述語の実行エラーなどで run が中断した場合：述語を直して再走する。

再走するときは、`git bisect log` を控えてから `git bisect reset` し、校正からやり直す。

## 名指しされたコミットを差分で確かめる

フレーキーさや skip の連続で、bisect が間違ったコミットを名指しすることがある。

- `git show --stat <first-bad>` と差分を読み、その変更で症状の出る箇所と条件を説明できるかを確かめる。
- 名指しされたのがマージコミットなら、`--first-parent` で探索し直さず、第 1 親との差分（`git diff <first-bad>^1 <first-bad>`）で分析し、マージだったことを弱点として報告する。
- 説明できれば、根拠とともに断定する。説明できなければ、断定せずにその旨を報告する。

## 報告して片付ける

報告には次を含める。bisect log はファイルにせず、報告の本文に載せる。

- 原因コミットの SHA、件名、作者、日付。収束しなかった場合は、候補のコミットの一覧と、それらが skip された理由。
- そのコミットの何が症状を起こすかの分析（差分に基づく）。
- `git bisect log`（辿った good / bad / skip の経路）。
- 検証の弱点：skip の多発、フレーキーさと反復回数、`-- <paths>` による絞り込み、マージコミットの名指し。

結論を出せずに止まった場合（収束しない、中断の原因が分からない、見積もりが長く走らせなかった）は、worktree と bisect の状態を調査用に残し、その場所と、片付けが未実施であることを報告に含める。
それ以外は次のとおり片付ける。

- worktree の中で `git bisect reset` を行い、そのあと `git worktree remove .wt/bisect` で worktree を消す（消し残りがあれば `git worktree prune`）。
- 述語スクリプトと、述語のために作ったコピーを消す。
- 再現テストは消さずに残す。修正に進むとき、修正前に失敗するテストとしてそのまま使えるためである。このスキルは修正に進まない。
