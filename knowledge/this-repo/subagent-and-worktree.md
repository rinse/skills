`concurrent-dev` と `gh-release` に共通する、Subagent の使い方と、その前提になるファイルアクセス許可の制約。

# 委譲するのは「機械作業」、判断は手元に残す

Subagent に委譲すべきなのは、**担当範囲だけを見れば進められ、他の作業とのずれを後段のレビューで正せる作業**のうち、オーケストレーターのコンテキストウィンドウを圧迫するもの。**一貫性と最終判断はオーケストレーターが握り続ける**。委譲の主目的はコンテキストウィンドウを空けておくことで、オーケストレーターはワークフロー全体を俯瞰し続け、各タスクを破綻なく遂行して方向性を維持できる。難易度に応じた安価なモデルの選択によるコスト削減は副次的な利点。これは [スキル設計の思想](/this-repo/skill-design-philosophy.md) の「核（判断）と機械作業の分離」を、コンテキスト配分とモデル選択の次元で実装したもの。

- `gh-release`: トークンを食う**差分の読解だけ**を Haiku の Subagent に委譲し、**事実抽出に徹させる**（bump 種別やバージョンは決めさせない）。最終的なバージョン判断・ノート合成・タグ作成はオーケストレーターが、自分が読んだログと Subagent の報告を突き合わせて行う。
- `concurrent-dev`: **テスト作成と実装**を難易度に応じて Haiku / Sonnet / Opus の Subagent に委譲。一見重要に見えるこれらは一貫性を保つうえでは些事で、むしろ細々して見えるタスク分解・準備（ブランチ・worktree 作成）・レビュー・マージ・後片付けが一貫性を左右するため、これらはオーケストレーターが行う。「全タスクの差分を一人が読む」ことが並列開発で崩れがちな一貫性（重複実装・命名のずれ）を守る唯一の方法、と明言。同じ基準で、タスク分解前のコードベース調査（結論だけ受け取る）と、出力の長いテスト・ビルドの実行と失敗の切り分け（進めるかの判断と、タスク間の意味的な衝突の調査は手元に残す）も委譲する。

# モデルは難易度で割り当てる

`concurrent-dev` の指針: 判断の余地がほぼない機械的タスクは **Haiku**、仕様が明確で局所的な変更・既存パターン踏襲・定型作業は **Sonnet**、設計判断・複数モジュール横断・曖昧さの残るもの・厄介なデバッグは **Opus**。迷ったら一段上のモデルに倒す前に「一段下のモデル + より具体的な指示」（Opus→Sonnet、Sonnet→Haiku）で届かないかを検討する。**弱いモデルほど指示を specific にする**——Subagent への指示は変更対象ファイル・倣うべき既存コード・受け入れ条件まで具体化し、モデルが弱くなるほどその解像度を上げる。

# worktree はプロジェクトルート直下（`.wt/`）に作る

これは見落としやすい**許可上の制約**。`concurrent-dev` は worktree を必ずプロジェクトルート直下の `.wt/` に作る。

- 理由: Claude Code のファイルアクセス・コマンド実行の許可は**プロジェクトディレクトリに対して**与えられている。その配下に worktree を置くことで Subagent が許可を引き継げる。
- やってはいけない: `/tmp` や Agent ツールの `isolation: "worktree"` が作るプロジェクト外の場所に作ること（許可が及ばず Subagent が作業できない）。
- 補足: `.wt/` は `.gitignore` ではなく `.git/info/exclude` に入れてリポジトリを汚さない。

この「プロジェクト外は許可が及ばない」という性質は Claude Code のランタイム特性に由来する（[ランタイムと配布](/agent-skills/runtime-and-distribution.md)）。
