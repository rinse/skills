# Skills

このリポジトリのスキルは `gh skill install` で個別に入れます。まとめて使うスキル群は `plugins/` にプラグインとして置いてあり、`claude plugin install` で入れます。

## インストール

### スキルを個別に入れる

```sh
gh skill install rinse/skills concurrent-dev
```

### プラグインを入れる

```sh
claude plugin marketplace add rinse/skills
claude plugin install traceless@rinse --scope project
```

プラグインのスキルは `<plugin>:<skill>` の名前空間に入ります（例: `/traceless:cleanup-comments`）。
`gh skill install` はプラグイン内のスキルも見つけますが、Claude Code が読まない二段のパス（`.claude/skills/<plugin>/<skill>/`）に置くので、プラグインは `claude plugin install` で入れてください。

## スキル管理のベストプラクティス

基本的にスキルはプロジェクト単位で管理することが推奨されます。

グローバルに置くと次のような問題があります。

1. そのリポジトリで利用しているスキルおよびそのバージョンが暗黙的になる
    * スキルの有無はエージェントの動きを大きく変えてしまいます
    * エージェントによる開発を中心に据えると、これは致命的です
2. スキルを利用しないエージェントのコンテキストウィンドウを圧迫する
    * スキルが誤発火しないことは重要だが、コンテキストウィンドウはモデルがどれだけ発展しても貴重です
    * スキルの description を短く保つ努力をしているにもかかわらず、不要なスキルを読む余裕はありません

よってグローバルに配置することを容認できるのは、この中だと git-init, gh-init 程度です。
それ以外はプロジェクト単位でインストールするべきです。

## スキルの一覧

### kickoff

プロジェクトを一から立ち上げるスキル。
`git-init` → `gh-init` でリポジトリを整え、`gh skill install` でプロジェクトの baseline スキル（`git-commit` / `okf-knowledge` / `technical-writing-ja` / `concurrent-dev` は常時、他の `git-*` はユーザー選択、`gh-*` はリモート作成時のみ全導入）を入れる。いずれのツール・スキルも無ければスキップする。最後に `README.md`（概要と docs/ へのリンク集）・`AGENTS.md`（概要とドキュメント管理規則、docs/・knowledge/ へのリンク）を軽量に作成し、`git-commit` でコミットして終了する。

### gh-pr-create

現在のブランチから GitHub の Pull Request を作成するスキル。
差分の全体を読んでタイトルと本文を合成し、リポジトリに PR テンプレートがあればそれに従う。push はまず一度試し、失敗すればユーザーに依頼する。作成前に内容を確認する。GitHub の PR 専用。

### gh-pr-update

既存の GitHub Pull Request の title・description・labels を最新の差分に合わせて更新するスキル。
レビュー指摘の反映・追加の指示・その他 PR の修正でコードを変えたときに、古い本文へ追記するのではなく現在の差分全体から再合成して、説明が実体とずれないようにする。更新前に変更内容を確認する。GitHub の PR 専用。

### create-issue

雑な記述から Issue を起票するスキル。
やりたいことを構造化された本文に合成し、リポジトリに ISSUE_TEMPLATE があればそれに従い、なければ概要・目的・制約・受け入れ条件のテンプレートを使う。GitHub なら `gh` で作成し、リモートが無い場合はマークダウンファイルとして書き出す。作成前に内容を確認する。

### gh-review

GitHub の Pull Request に対してコードレビューを行うスキル。
変更を確認し、該当する行に severity タグ付きのインラインコメントを投稿する。GitHub の PR 専用。

### gh-address-review

自分の PR に付いたレビュー指摘に対応するスキル。
各指摘を「対応する・押し返す・質問で返す・対応不要と説明する」の 4 つに分類し、分類表と返信文をユーザーに確認してから、修正・返信・スレッドの resolve までを行う。設計意図と衝突する指摘に盲従しないことが核。resolve は修正して push した指摘に限り、押し返しは 1 往復まで。対応後の本文更新は gh-pr-update に委譲する。GitHub の PR 専用。

### gh-release

最後のリリース以降の差分を読み、新しいセマンティックバージョンを切るスキル。
トークンを食う差分の読解は Haiku の Subagent に委譲し、オーケストレーターがログと報告を突き合わせて bump 種別（major/minor/patch）を判断して次バージョンを算出する。リリースノートを合成して注釈付きタグを作成、任意で GitHub Release も作る。0.x の特例（破壊的変更でも minor）に対応し、push はまず一度試し、失敗すればユーザーに依頼する。作成前に内容を確認する。

### gh-init

ローカルの git リポジトリに対して GitHub 上のリモートリポジトリを作成するスキル。
`gh`（なければ GitHub MCP）でリポジトリを作成して `origin` として登録する。push はまず一度試し、失敗すればユーザーに依頼する。

### git-commit

git のコミットを行うスキル。
変更内容を確認し、単一行のコミットメッセージでコミットする。

### concurrent-dev

複数の開発タスクを並列に進めるスキル。
オーケストレーター（Fable 5 / Opus 級）が依存関係・優先順位・競合を判断して実行計画を立て、プロジェクトルート下 `.wt/` の worktree を準備し、開発作業だけを想定難易度に応じた Haiku / Sonnet / Opus の Subagent に委譲してコストを削減する。レビュー・マージ・後片付けはオーケストレーター自身が行い、一貫性を保つ。依存で一本鎖になるタスクは無理に並列化せず直列で進める。

### git-init

git リポジトリを初期化するスキル。
`git init` を実行し、git プロファイル（ユーザー名・メールアドレス）を切り替えて、空の初期コミットを作成する。

### okf-knowledge

作業で得た知見を [Open Knowledge Format (OKF)](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) の knowledge bundle として残すスキル。
「知見を貯めて」「知見をまとめて」をトリガーに、再利用価値のある知見を抽出して `knowledge/`（既定はプロジェクトルート直下）に OKF 準拠の concept ファイルとして書き出す。`index.md` は常に維持し、`log.md` は git 管理下なら作らず・非管理ならユーザーに確認（既存なら維持）、`AGENTS.md` と `CLAUDE.md` は両方確認し、存在する方（両方あれば `AGENTS.md` を優先）に bundle へのポインタが無ければ追記を確認する。書式の機械的な踏襲より「何をどの粒度で concept にするか」の判断に重きを置く。

### technical-writing-ja

日本語の技術文書を書く・直すときの文章規範を提供するスキル。
整形・段落と論証の構成・論証の厳密さ・読み手の負荷管理・演出の抑制・LLM っぽい表現の禁止・冗長の排除といった規範を、出典の gist に基づいてまとめている。

### skill-creator

このリポジトリの規約に沿って Agent Skill を新しく書く、または既存のスキルを直すスキル。
中心にあるのは、書こうとしているスキル固有の判断（機械的なコマンドでは埋められない、そのスキルにしかない判断）を見つけて本文をそれに使うこと。カジュアルな依頼を、スキル固有の判断、発火する場面、入出力の形式の可能性に展開し、分かれる点をユーザーに質問して仕様を確定してから、本文に畳み込む。判断の候補が残らない処理はスクリプトで足りるとしてスキルにしない。英語の短い description、日本語の本文、手順書より判断を書くこと、稀な経路の `references/` への分離、検証と README 更新までを扱う。外部に作用するスキル向けの取り決め（了承を取る箇所、副作用の強い選択肢、失敗時に残った状態の扱い）は `references/side-effects.md` に、Subagent に委譲するスキル向けの取り決め（委譲の範囲、渡すものと受け取るもの、モデルの選び方）は `references/orchestration.md` に分け、展開のときに読む。frontmatter の仕様やリンク切れのような機械的に決まる検査は `scripts/check.js`（Node.js 標準ライブラリのみ）が行う。ベンチマーク eval は扱わない。

### traceless（プラグイン）

完成したコードと文書を、差分や会話を見ずに読み、編集の残滓を削るスキル群。`plugins/traceless/` として配布する。

- **cleanup-speculation**: 到達不能な防御、呼び出し元が一箇所しかない抽象化、常に既定値で呼ばれるオプション、旧形式を受け付ける分岐や呼び出し元のない関数、`fooV2` `legacyBar` のように存在しない概念を指す名前を対象に、「現在のコードベースにそれを発生させる呼び出し元があるか」で判断する。外部入力の境界の検証は残す。
- **cleanup-tests**: 実装のコピー、モックの自己検証、型・ライブラリ保証の再確認、重複、過剰なケース分け、偶然の性質の固定、変更に由来するテスト名を対象に、「削除するとどんな現実的な不具合を見逃すか」「実装を見ずに仕様だけから書けるか」で判断する。件数やカバレッジの維持自体は目的にしない。
- **cleanup-comments**: 変更の叙述、作業報告、コードの言い換え、コメントアウトされたコード、担当者も期限もない TODO を対象に、「一発書きしたときにこのコメントを書くか」で判断する。次の編集者を制約する情報と、ドキュメント生成の入力は残す。
- **cleanup-docs**: 旧状態の否定、変更の物語化、理由の混入、付記、「また」「なお」の堆積、会話の漏出を対象に、「初見の読者が編集されたものだと気づけるか」で判断する。修正は文単位でなく段落・節の単位で事実から書き直す。CHANGELOG・ADR・移行ガイドには適用しない。

- **cleanup**: 指定したファイル（指定が無ければ未コミットの変更ファイル）に四つのスキルを speculation → tests → comments → docs の順に適用する。各スキルは会話と差分を持たない別の Subagent で実行し、最後にクリーンアップによる変更の確認と test / build / lint を行って報告する。`/traceless:cleanup` で明示的に起動する。

### loop-dev（プラグイン）

着手してよい（ready の）Issue を 1 件ずつ、選定 → 実装 → 納品 → 新しい Issue の起票 の順に処理し、ready の Issue が無くなるまで繰り返すスキル群。`plugins/loop-dev/` として配布する。Issue は GitHub Issues（`ready` ラベル）とローカルファイル（`issues/*.md` の frontmatter `status: ready`）の両方を扱う。どの Issue を ready にするかと、納品物を受け入れるかは人間が決める。

- **loop-dev**: ループ全体のオーケストレーター。各段階を Subagent に任せ、段階の間の判断だけを行う。GitHub の Issue はドラフト PR、ローカルの Issue はベースブランチへの squash マージで納品する。新しい Issue は README などから読み取れるプロジェクトの目標と現状の差から起票し、明確な案が無ければ起票しない。`/loop-dev:loop-dev` で起動する。
- **pick-issue**: ready の Issue から、優先度・Issue 間の依存・リポジトリの状態で次の 1 件を選んで確保する。受け入れ条件が無い、記述が矛盾しているなど、人間が直さないと着手できない Issue は blocked にして差し戻す。
- **concurrent-dev**: 同名スキルの loop-dev 向けの版。計画を `plan.json` に書き、スクリプトによる機械検査と、文脈を共有しない Subagent によるチェックリスト審査を通してから着手する。
- **create-issue**: 同名スキルの loop-dev 向けの版。ローカルの Issue に frontmatter（`status`、`priority`）を付ける。
- **git-commit**、**gh-pr-create**、**gh-pr-update**: 同名スキルと同じ内容。

### playwright-cli-auth

playwright-cli で認証をユーザーに行わせるスキル。
認証時だけ playwright-cli を headful で表示し、ユーザーにログイン操作を行わせた後、headless モードに戻って操作を続行する。

### inspect-web-traffic

ブラウザ操作の裏で流れる通信を解析し、その操作を再現するワンショットスクリプト（既定は curl、指示があれば TypeScript / Python）を合成するスキル。
まず playwright-cli 単体で通信を捕捉し、`request`／`response-body` を材料に「どのリクエスト群がその操作か」を選んでノイズを削り秘密情報をパラメータ化し、リプレイで再現を検証する（捕捉のダンプではなく合成が核）。自動化検知・captcha・ログインで阻まれたら、システムの Chrome を明示プロファイル + CDP ポート + netlog で起動して `attach --cdp` でアタッチし、検知回避とユーザー支援を得つつセッション全体を netlog に記録する。ブラウザの HTTP(S) 通信専用。

### git-bisect

回帰バグの原因コミットを `git bisect` で特定するスキル。
核は `git bisect run` に渡す述語スクリプト（ビルド失敗は 125 で skip、症状の有無を 0/非 0 に変換）の合成で、各ステップをエージェントが手で試すことを禁じ、反復は bisect に委ねる。再現手段が無ければ、単一コマンドで症状が出たら非 0 で終わる再現コマンドを先に作り、述語に包む。本走前に bad/good 両端で述語を校正し、名指しされたコミットは差分で症状を説明できるか検証してから報告する。専用 worktree（`.wt/bisect`）で回し、修正はしない。

### adversarial-panel

複数モデルによる敵対的相互レビューを、メインセッションがファシリテーターとして統合するスキル。
2〜4 名のパネリスト（外部 CLI → 別 Claude モデル → 同一モデルの手法分け、の順で異種性を最大化）が独立に回答し、互いの主張を検証可能な形で批判し、批判を受けて最終立場を出す 3 ラウンドを回す。核は独立性（初回は互いの回答を見ない）・敵対性（新しい論拠のない同意は失敗）・平均化しない統合（対立点は残して裁定する）の 3 つの不変条件で、合意点・対立点・較正された確信度と反証条件を一つの回答にまとめる。「議論させて」「red-team this」「本当に合ってる？」で発動する。

### spike

実装タスクの実現可能性が不透明なとき、使い捨てのプロトタイプで不透明さを潰し、知見を技術文書として回収するスキル。
核は 2 つの規律 ── 実現可能性が不透明な最小の部分だけを突く（1 スパイク 1 問い）ことと、知見をコンテキストではなく単体で完結する文書（`docs/spikes/`）に回収すること。調査するエージェントと実装するエージェントは別（オーケストレーターが調査を Opus・実装を Sonnet の Subagent に振る）前提で、作業ツリーの本番コードは改変せず `.spike/` にのみ書く。検証が in-place 改変を要する場合だけ使い捨て worktree（`.wt/spike-<slug>`）に隔離し回収後に破棄する。文書は問い → 結論（＋推奨）→ 詳細 → Why not（採らない道）→ 落とし穴（採る道の罠）の体裁で、実装そのものはせず引き継ぐ。

### dads-ui-design

[デジタル庁デザインシステム（DADS）](https://design.digital.go.jp/dads/) v2.18.0 に沿って Web の UI を設計・実装・レビューするスキル。
核は、情報の意味に合うコンポーネントを選ぶことと、外観を導入先に合わせて変えてもアクセシビリティの骨格（コントラスト比、文字サイズ、フォーカスインジケーター、ターゲットサイズなど）を崩さないこと。
設計の前に導入先のローカルデザインシステム（スタイルガイド）を決める。`docs/design-system.md` などの既存のものを探し、無ければ「既存のものを使う」「キーカラーなど決まっている値だけ指定して残りを DADS の様式で導出する」「DADS の初期値をそのまま使う」から選んでもらい、結果を `docs/design-system.md` に記録する。キーカラーは `scripts/contrast.py --key` で、DADS のコードスニペットが使う 15 組の色の組み合わせを検証する。
SKILL.md には哲学、編集できる範囲と守る要件、基本の値だけを置き、ローカルデザインシステムの作り方、基本デザインの詳細、デザイントークンの実値、全コンポーネントの使い分けと規範、外部リソースとライセンスは `references/` に分けている。

## SKILL.md の検証

`push` 時に GitHub Actions（`.github/workflows/validate-skills.yml`）が各 `skills/*/SKILL.md` を検証する。

- **妥当性チェック（エラー、CI を失敗させる）**: [`skills-ref`](https://github.com/agentskills/agentskills/tree/main/skills-ref) reference library による Agent Skills 仕様準拠チェック（必須フィールド・文字数上限・命名規則・ディレクトリ名との一致など）。
- **ベストプラクティスチェック（警告、CI は失敗させない）**: `name` + `description` の推定トークン数が、常時ロードされる Level 1 メタデータの目安である 100 トークンを超えていないか。

ローカルで同じチェックを実行するには([uv](https://docs.astral.sh/uv/) を使う。`skills-ref` は実行時に自動でインストールされる):

```sh
uv run scripts/validate_skills.py
```

特定のスキルだけ検証する場合はパスを渡す（`--strict` を付けると警告もエラー扱いになる）:

```sh
uv run scripts/validate_skills.py skills/gh-pr-create --strict
```
